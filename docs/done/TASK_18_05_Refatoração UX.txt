# TASK CARD — Refatoração UX/UI Dashboard (Serviços, Bloqueios e Padronização Visual)

## Contexto

Realizar melhorias visuais, responsivas e de experiência do usuário nas áreas de:

* Serviços
* Bloqueios de agenda
* Feedbacks de erro
* Padronização global de botões

A implementação deve seguir:

* Design system atual do projeto
* Padrões de cores já existentes
* Responsividade mobile-first
* UX moderna e minimalista
* Consistência visual entre telas/dialogs
* Acessibilidade básica (focus, contraste, áreas clicáveis)

A IA deve assumir que já conhece:

* arquitetura do projeto
* stores
* services
* interceptors
* componentes compartilhados
* padrões Angular Material utilizados no app

---

# DIRETRIZES GERAIS

## UX/UI

* Priorizar experiência mobile.
* Garantir excelente usabilidade em telas pequenas.
* Evitar poluição visual.
* Utilizar hierarquia visual clara.
* Evitar layout shift.
* Melhorar percepção de estado e feedback visual.
* Garantir consistência entre telas.

---

# IMPORTANTE — PESQUISA DE COMPONENTES/PLUGINS

Antes de implementar:

* Buscar bibliotecas/plugins já utilizados no ecossistema Angular Material.
* Priorizar reaproveitamento de componentes prontos.
* Evitar criar soluções complexas do zero.

Avaliar especialmente:

* grids responsivos
* skeleton loaders
* empty states
* chips/badges
* calendários/listagens
* toggles modernos
* hover actions
* loading placeholders

Preferir:

* Angular Material
* CDK
* libs leves e maduras
* componentes compatíveis com Angular atual do projeto

Evitar:

* bibliotecas abandonadas
* libs pesadas
* dependências desnecessárias

# 2.1 Feedback visual e validação

## Problema atual

Usuário não entende por que o formulário está inválido.

Necessário melhorar feedback inline.

---

## Melhorias obrigatórias

### Campo Data

Adicionar:

* `required`
* `mat-error`
* estado visual inválido
* mensagem clara abaixo do campo

Exemplos:

* “Informe uma data”
* “Data inválida”

---

### Forms

Avaliar migrar para Reactive Forms.

Objetivo:

* consistência com `servico-dialog.component.ts`
* melhor controle de validação
* código mais previsível

Se não migrar:

* justificar tecnicamente

---

### Hora início / Hora fim

Trocar validações via snackbar por:

* `mat-error`
* feedback inline

Exemplos:

* “Informe horário inicial”
* “Informe horário final”
* “Hora final deve ser maior que hora inicial”

Snackbar deve ser usado apenas para erros globais.

---

### Tratamento de erro backend

No `catch` do `salvar()`:

Exibir mensagem real da API quando disponível.

Exemplo:

* backend retorna 400:
  “Já existe bloqueio nesse horário”

Não usar fallback genérico sempre.

Fallback genérico:

* apenas quando não houver mensagem válida

---
